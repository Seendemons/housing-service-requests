# housing-service-requests

Репозиторий проекта для работы с заявками в жилищную службу.

Проект находится на начальном этапе разработки. Приложение FastAPI поддерживает
вход жителей и диспетчеров, серверные сессии, создание и редактирование
черновиков, ручную отправку и просмотр своих заявок с историей.

## Окружение разработки

Используются Python 3.13 и менеджер зависимостей uv.

Из корня проекта выполните:

```bash
uv sync
uv run python --version
```

`uv sync` создаёт окружение `.venv` и устанавливает зависимости по `uv.lock`.
`uv run` запускает команды в окружении проекта без ручной активации.
Ожидаемая версия Python — 3.13.x.

В PyCharm выберите существующий интерпретатор `.venv/bin/python`
в настройках Python Interpreter.

## Запуск приложения

Из корня проекта выполните:

```bash
uv run uvicorn app.main:app --reload
```

Откройте <http://127.0.0.1:8000/> — появится главная страница и ссылка на вход.
Документация API доступна по адресу <http://127.0.0.1:8000/docs>.

`app.main:app` указывает на объект `app` в файле `app/main.py`.
Uvicorn запускает веб-сервер, а `--reload` перезапускает его после изменений
Python-кода. Этот режим предназначен для локальной разработки.
Чтобы остановить сервер, нажмите `Ctrl+C` в терминале.

## Настройки приложения

Без `.env` приложение работает с настройками по умолчанию. При необходимости
создайте локальный файл из безопасного шаблона (из корня проекта):

```bash
cp -n .env.example .env
```

Команда не перезаписывает существующий `.env`. Отредактируйте его при необходимости:

- `APP_NAME` — непустое название приложения; по умолчанию «Заявки в жилищную службу».
- `APP_DEBUG` — режим отладки FastAPI: `true` или `false`, по умолчанию `false`.

`.env` загружается автоматически из корня проекта независимо от каталога запуска;
переменные окружения имеют приоритет. Локальная `.env` игнорируется Git,
а `.env.example` хранится в репозитории только как шаблон и сам не загружается.
Команда запуска остаётся прежней.

## PostgreSQL через Docker Compose

Подготовлена конфигурация PostgreSQL 17 и слой подключения через SQLAlchemy.
Для запуска БД нужны установленный Docker с работающим Docker Engine
и Docker Compose v2 (`docker compose`). Локальный запуск PostgreSQL, сохранение
данных после перезапуска и подключение через SQLAlchemy проверены.

Из корня проекта создайте `.env` без перезаписи существующего файла:

```bash
cp -n .env.example .env
```

Если `.env` уже существует, вручную добавьте в него недостающие `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_PORT` из `.env.example`,
сохранив свои настройки приложения. Замените вымышленный пример пароля своим
непустым паролем перед запуском. Переменные окружения имеют приоритет над `.env`.

После установки Docker проверьте конфигурацию без вывода значений и секретов:

```bash
docker compose config --quiet
```

Для запуска и проверки состояния:

```bash
docker compose up -d db
docker compose ps
```

После инициализации ожидается состояние `healthy` у сервиса `db`.
При подключении приложения с этого компьютера используйте хост `127.0.0.1`,
порт из `POSTGRES_PORT` (по умолчанию `5432`), имя БД из `POSTGRES_DB`,
пользователя из `POSTGRES_USER` и пароль из `POSTGRES_PASSWORD`.
`POSTGRES_HOST` задаёт хост приложения и по умолчанию равен `127.0.0.1`;
Compose его не использует. В шаблоне имя БД — `housing_requests`,
пользователь — `housing_user`.
Порт БД доступен только на локальном интерфейсе компьютера.

Проверить соединение с запущенной БД из корня проекта можно командой:

```bash
uv run python -c $'from sqlalchemy import text\nfrom app.database import get_engine\nwith get_engine().connect() as connection:\n    print(connection.scalar(text("SELECT 1")))'
```

При успешном соединении команда выводит `1`. `app.database.get_engine()`
лениво создаёт и сохраняет engine; сам вызов без запроса соединения с сервером
не устанавливает. `get_db()` — зависимость FastAPI для синхронной `Session`:
она закрывает сессию и откатывает транзакцию при ошибке. Автоматического
`commit()` нет: успешные изменения обработчик должен подтвердить явно.
Перезапустите приложение после изменения настроек БД, чтобы создать новый engine.
Главная страница и импорт приложения работают без запущенной БД.

Пример использования зависимости в обработчике FastAPI:

```python
from fastapi import Depends
from sqlalchemy.orm import Session

from app.database import get_db


def example_handler(db: Session = Depends(get_db)):
    # Здесь можно выполнить запросы через db.
    # После нужных изменений вызовите db.commit().
    pass
```

Для остановки:

```bash
docker compose down
```

Именованный том `postgres_data` сохраняет данные после `docker compose down`.
Переменные `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` применяются при
первой инициализации пустого тома. Изменение `.env` не меняет автоматически
пароль, пользователя или имя уже созданной БД.

Справка: [официальный образ PostgreSQL](https://hub.docker.com/_/postgres),
[проверка конфигурации Compose](https://docs.docker.com/reference/cli/docker/compose/config/)
и [остановка Compose](https://docs.docker.com/reference/cli/docker/compose/down/).

## Модели и миграции

Схема содержит пользователей (`users`), исполнителей (`executors`), заявки
(`service_requests`) и историю изменений статуса (`request_history`).
Роли: `resident` (житель), `dispatcher` (диспетчер). Исполнители — отдельный
справочник. Статусы заявки: `draft`, `new`, `in_progress`, `closed`;
начальный статус — `draft`. Заявка принадлежит
пользователю и может иметь исполнителя; история связана с заявкой и автором
записи. Связанные записи защищены от удаления ограничениями внешних ключей.
Модели хранят хеш пароля. При отправке черновика переход `draft → new`
записывается в историю вместе с автором и временем одной транзакцией.
Даты создаются в UTC на стороне ORM;
для прямых вставок база также задаёт
текущее время. `updated_at` обновляется автоматически при изменениях через
SQLAlchemy, триггера в базе нет. SQLite не сохраняет сведения о часовом поясе
при чтении дат.

После настройки подключения к PostgreSQL примените миграцию из корня проекта:

```bash
uv run alembic upgrade head
uv run alembic current
```

Первая команда создаёт таблицы, вторая показывает текущую ревизию. Начальная
миграция 0001 отдельно проверена на PostgreSQL 17.11: применение, откат,
повторное применение, связи моделей и ограничения БД.

## Вход и демо-пользователи

После настройки PostgreSQL и применения миграций задайте в локальном `.env`
непустые `DEMO_RESIDENT_PASSWORD` и `DEMO_DISPATCHER_PASSWORD`. Выберите свои
пароли; шаблон `.env.example` оставляет эти значения пустыми. Создайте пользователей:

```bash
uv run python -m app.seed_demo
```

Логины: `resident` и `dispatcher`. Повторный запуск сохраняет существующие
пароли и роли. При конфликте роли операция откатывается целиком. Переменные
окружения имеют приоритет над `.env`.

Откройте `/login`, войдите под нужным логином и паролем; кабинеты доступны по
адресам `/resident` и `/dispatcher`, выход — в личном кабинете. Серверная
сессия действует до восьми часов; браузер хранит её идентификатор в cookie,
а формы входа и выхода защищены CSRF-токеном. Для локального HTTP задайте
`SESSION_COOKIE_SECURE=false`; при работе через HTTPS установите
`SESSION_COOKIE_SECURE=true` и перезапустите приложение.

## Заявки жителя

Войдите как житель и откройте `/resident`. Нажмите «Создать черновик», укажите
местоположение проблемы и описание, затем нажмите «Сохранить черновик».
Местоположение обязательно и ограничено 255 символами, описание — 10 000
символами. Пробелы по краям удаляются; пустые поля не сохраняются. При ошибке
форма показывает пояснение и сохраняет введённый текст.

После сохранения открывается карточка черновика. Вернуться к нему можно
из списка в кабинете: новые записи показываются первыми. Черновики сохраняются
в PostgreSQL и доступны после повторного входа. В кабинете видны свои заявки
всех статусов, включая черновики; диспетчер доступа к этим страницам не имеет.
Сохранение формы защищено CSRF-токеном.

В карточке нажмите «Редактировать», измените местоположение или описание и
нажмите «Сохранить изменения». Откроется карточка с обновлённым текстом.
«Отмена» возвращает в карточку без сохранения. Редактировать можно только свой
черновик; действуют те же ограничения полей и защита CSRF. Время обновления
меняется при сохранении, дата создания сохраняется.

Чтобы передать черновик, в его карточке нажмите «Отправить диспетчеру».
Статус изменится на «Новая», а в истории появится переход «Черновик → Новая»
с логином автора и временем UTC. Пока ИИ не подключён, отправка выполняется
вручную. После отправки редактирование недоступно, но карточка и история
остаются доступны владельцу. Повторная отправка возвращает в карточку
и не создаёт повторной записи истории. Отправка защищена CSRF-токеном;
при ошибке записи статус и история откатываются вместе.

Кабинет диспетчера пока содержит только данные аккаунта; просмотр отправленных
заявок диспетчером — следующий этап. Вложения и проверка ИИ ещё не реализованы.
Используются существующие таблицы; новых миграций нет.

## Структура

```text
app/
  __init__.py
  config.py             # Настройки приложения и БД, чтение .env
  database.py           # Engine и сессии SQLAlchemy
  models.py             # Модели данных, включая серверные сессии
  auth.py               # Хеширование паролей и проверка сессий
  seed_demo.py          # Явное создание демо-пользователей
  main.py               # Маршруты приложения
  templates/            # Главная, вход, кабинеты и черновики заявок
alembic.ini             # Настройки запуска Alembic без пароля
migrations/             # Миграции 0001 и 0002 и окружение Alembic
pyproject.toml          # Настройки проекта и зависимости
uv.lock                 # Зафиксированные версии зависимостей
```

FastAPI обрабатывает запрос браузера, Jinja2 формирует HTML по шаблону,
а Uvicorn принимает HTTP-запросы и передаёт их приложению.

## Проверки

Из корня проекта установите зависимости разработки и выполните проверки:

```bash
uv sync --dev
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

Ruff проверяет код и форматирование, а pytest проверяет настройки, главную страницу,
авторизацию, сессии, создание, редактирование, отправку, историю и доступ
к своим заявкам, модели и миграции на SQLite,
а также генерацию SQL для PostgreSQL.
Эти тесты не требуют PostgreSQL и сами по себе не подтверждают работу входа
в браузере с настоящей БД или миграций и ограничений на PostgreSQL; описанная выше проверка на PostgreSQL выполнена отдельно.

Создание и просмотр черновиков также отдельно проверены в браузере на временной
PostgreSQL 17 с миграциями 0001/0002: сохранение после повторного входа,
изоляция жителей, запрет доступа диспетчеру, ошибки формы и ширина экрана
320 пикселей. Тестовая БД удалена после проверки; проектные данные не менялись.

9 ноября 2026 года ручная отправка отдельно проверена через TestClient
на временной PostgreSQL 17 с миграциями: сохранение статуса и истории,
повторный вход, права доступа, CSRF, откат при ошибке записи истории,
одновременная отправка из двух сессий без дублей и запрет сохранения
ранее открытой формы после отправки. Проверка была одноразовой;
браузер на этом этапе не использовался. Рабочая БД и её тома не менялись.
